# 06 — Mock ZainCash Wallet API

A small Hono + SQLite service that behaves like a wallet backend. It is **not** ZainCash's real API and must never be presented as one. Label it "Mock wallet (synthetic)" in the UI.

## Data model (SQLite)

```sql
users(id TEXT PK, name TEXT, phone TEXT UNIQUE, balance_iqd INTEGER, daily_limit_iqd INTEGER, created_at)
contacts(id TEXT PK, owner_id TEXT FK, display_name TEXT, name_normalised TEXT,
         relation TEXT NULL,            -- "أم","أخ","خال"...
         phone TEXT, wallet_user_id TEXT NULL, last_used_at)
billers(id TEXT PK, code TEXT,          -- electricity|generator|internet|water|mobile_topup
        name_ar TEXT, name_en TEXT, aliases TEXT,  -- JSON array: ["الكهرباء","الكهربا","كهرباء الوطنية"]
        status TEXT CHECK(status IN ('active','down','maintenance')))
bill_accounts(id TEXT PK, owner_id TEXT, biller_id TEXT, account_ref TEXT, nickname TEXT NULL)
bills(id TEXT PK, account_id TEXT, amount_iqd INTEGER, due_date TEXT, status TEXT CHECK(status IN ('unpaid','paid')))
transactions(id TEXT PK, owner_id TEXT, kind TEXT, counterparty TEXT, amount_iqd INTEGER, fee_iqd INTEGER,
             status TEXT, idempotency_key TEXT UNIQUE, created_at)
confirmation_tokens(token TEXT PK, session_id TEXT, payload_hash TEXT, expires_at, used_at NULL)
idempotency_keys(key TEXT PK, request_hash TEXT, response_json TEXT, status_code INTEGER, created_at)
audit_log(id INTEGER PK AUTOINCREMENT, ts, session_id, event, data_json)
```

All money is **integer IQD**. No floats anywhere.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/users/:id` | Profile + balance |
| GET | `/users/:id/contacts?q=` | Contacts (server-side fuzzy search optional; resolver also runs in core) |
| GET | `/billers` | Catalogue with status |
| GET | `/users/:id/bill-accounts` | Linked bill accounts + current unpaid bill |
| GET | `/users/:id/transactions?limit=&idempotencyKey=` | History / outcome lookup |
| POST | `/quotes` | Pre-check: `{kind, to, amount}` → `{ok, fee, balanceAfter, errors[]}` (no side effects) |
| POST | `/transfers` | Execute P2P. Headers: `Idempotency-Key`, `X-Confirmation-Token` |
| POST | `/bill-payments` | Execute bill. Same headers |
| POST | `/admin/faults` | Demo/eval only: inject latency, timeout-after-commit, 5xx, biller down |
| POST | `/admin/reset` | Reset DB to seed (eval runs) |

## Execute semantics (the important part)

```
POST /transfers
Idempotency-Key: 7f3c...          (UUIDv4, generated by client when the card is shown)
X-Confirmation-Token: ct_...      (issued at AWAITING_CONFIRM)
{ "from":"u_001", "to_contact":"c_014", "amount_iqd":50000 }
```

Server, inside **one SQLite transaction** (`BEGIN IMMEDIATE`):
1. Look up `idempotency_keys[key]`.
   - Exists and `request_hash` matches → return stored response (**HTTP 200, same body, header `Idempotent-Replay: true`**). No debit.
   - Exists and hash differs → **422 `IDEMPOTENCY_KEY_REUSED`** (IETF draft-ietf-httpapi-idempotency-key-header-07 §2.7).
   - A concurrent request waits for the atomic transaction, then replays the stored result; no in-progress response is emitted.
2. Validate token: exists, unused, not expired, `payload_hash === hash(body)`. Otherwise **403 `CONFIRMATION_INVALID`**.
3. Check balance + limit + biller status. On failure → 422 with a code. Store the failure response under the key too, so the outcome stays stable.
4. Debit/credit, insert transaction, mark token used, store response under key.
5. COMMIT.

## Error codes (map 1:1 to dialect copy in docs/15)

| Code | HTTP | Meaning |
|---|---|---|
| `INSUFFICIENT_BALANCE` | 422 | balance < amount + fee |
| `LIMIT_EXCEEDED` | 422 | daily or per-tx limit |
| `CONTACT_NOT_FOUND` | 404 | |
| `BILLER_UNAVAILABLE` | 503 | biller status ≠ active |
| `BILL_ALREADY_PAID` | 409 | |
| `CONFIRMATION_INVALID` | 403 | missing/expired/used/mismatch |
| `IDEMPOTENCY_KEY_REUSED` | 422 | same key, different payload |
| `AMOUNT_CHANGED` | 409 | bill amount differs from the quoted card amount → new card |
| `SERVICE_UNAVAILABLE` | 503 | injected outage |

## Fault injection (for "break it on purpose")

`POST /admin/faults {"mode":"timeout_after_commit","count":1}`. The server commits the debit, then sleeps past the client timeout. The client retries with the same key → the server replays the stored result → **one debit**. This is shown live in the demo.

Other modes: `latency_ms`, `error_5xx_before_commit`, `biller_down:<code>`.

## Fees and limits (as built, 2026-10-16)
Copied from ZainCash's public "Fees & Limits (Individual Wallet)" page, in `apps/wallet-api/src/fees.ts` with source and date:
- P2P: **0.5% of the amount, min 300, max 2,500 IQD** (so 50,000 → fee 300; 200,000 → 149,700 after the hero transfer).
- Bills: no additional fee (per-account `fee_iqd` exists in the seed and is 0 unless set).
- Monthly limits: transfers 2,500,000; mobile top-up 2,000,000; bills 10,000,000. Wallet capacity 10,000,000.
Fees are always shown on the card, even when 0. The early "P2P 0 IQD" plan was replaced.


## As built (M2, apps/wallet-api): differences and additions
- **Token issue endpoint:** `POST /confirmation-tokens {session_id, payload}` -> `201 {token, payload_hash, expires_at}`. The orchestrator calls it when the card is created. Token value is never written to the audit log.
- **Execute bodies:** transfer `{session_id, from, to_contact, amount_iqd}`; bill `{session_id, from, bill_account, amount_iqd?}`. **The orchestrator must always send the amount shown on the card**, so a bill that changed meanwhile returns `409 AMOUNT_CHANGED` instead of silently charging more (PSD2-style).
- **Order inside the one `BEGIN IMMEDIATE` transaction:** idempotency lookup -> token check -> business checks -> consume token (single-use enforced by the UPDATE) -> debit/credit -> insert transaction -> store response -> audit.
- **409 IDEMPOTENCY_IN_PROGRESS is never emitted.** There is no in-flight state: check and execute are one atomic transaction, so concurrent duplicates are serialised and the later ones are replays (`Idempotent-Replay: true`). Proved across 1 process, 2 connections and 4 OS processes (eval/results/wallet-safety-stress.json).
- **Stored vs not stored:** deterministic outcomes (404/409/422) are stored under the key; 400/403/503 are not (a retry with the same key can still succeed).
- **Extra error codes:** CONTACT_NOT_WALLET_USER 422, INVALID_AMOUNT 422 (not a multiple of 250), AMOUNT_REQUIRED 400, BILL_ACCOUNT_NOT_FOUND 404, USER_NOT_FOUND 404.
- **Fees** go to the biller settlement account (amount + fee), so total money is conserved (`SUM(users)+SUM(settlements)` is constant).
- **Faults:** `POST /admin/faults {mode, count, ms?, sleep_ms?, biller?}`; `biller_down` persists until `/admin/reset`. Admin needs `DEMO_MODE=1` and `X-Admin-Secret`; the server refuses to start with DEMO_MODE and no secret.
- **Run:** `pnpm --filter @zc/wallet-api dev` (DB_PATH for a file DB). `pnpm stress` regenerates the measured safety report.
